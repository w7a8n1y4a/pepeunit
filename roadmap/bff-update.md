# Изменения бекенда


## owner

1. Получить можно только скриптом запущенным из контейнера бекенда
1. Скрипту потребуется uuid пользователя
1. owner может выдавать роль админа
1. изначально на инстансе создаются только user
1. owner может быть только 1 на инстанс, все старые owner затираются перед присвоением нового

## Добавление instance_settings и мерж сервисов

    - в таблице будет только 1 строка

## Глобальный аккаунт

1. Старых пользователей считаем что нет при миграции
1. user login должен стать не уникальным
1. из user удаляются поля: hashed_password, cipher_dynamic_salt ну и из бекенда всё что для них было нужно то же. Добавляются public_key и hash_public_key
1. Из бекенда выпиливается ограничение на частоту обновления user, last_update_datetime и связанная с ним переменная в settings_instance удаляется
1. Алгоритм ключей - ML-DSA-87
1. Аутентификация на основе ключей ML-DSA-87, флоу ниже

### Флоу

Пользователь — это пара ключей. На инстансе личность — уникальный публичный ключ. Промежуточный ключ и ключи инстансов не используются. Пароли для аутентификации не используются.

| # | Этап | Что происходит | Ключи |
|---|---|---|---|
| 1 | Глобальная регистрация | Клиентское приложение создаёт пару ключей. Сеть не нужна. | Публичный и приватный ключ пользователя, ML-DSA-87. Приватный остаётся у пользователя. Публичный — личность аккаунта. |
| 2 | Регистрация на инстансе | Вместо логина и пароля пользователь на инстансе определяется уникальным публичным ключом. В user пишутся public_key и hash_public_key. | На инстанс передаётся только публичный ключ. Приватный не передаётся. |
| 3 | Запрос challenge | Клиент запрашивает у бекенда challenge JWT и передаёт хеш своего публичного ключа. Challenge — одноразовый пропуск на этот инстанс, срок 1–2 минуты, внутри домен инстанса. | Бекенд находит пользователя по hash_public_key и подписывает challenge своим секретом. |
| 4 | Подпись challenge | Клиент подписывает полученный challenge JWT приватным ключом пользователя. | Приватный ключ пользователя. |
| 5 | Проверка | Бекенд принимает ответ, если подпись пользователя сходится с public_key, сходится его собственная подпись challenge, срок жив, домен внутри токена его, и этот challenge ещё не использован. | Проверка идёт по public_key из user. Приватный ключ на инстанс не приходит. |
| 6 | Выдача JWT | Если проверки прошли, бекенд выдаёт JWT той же структуры, что текущий auth-токен. Отдельный механизм отзыва не нужен: блокировка пользователя уже есть. | Токен подписывает секрет инстанса pu_secret_key. Challenge помечается использованным. |

- Пункты 3–6 могут повторяются на каждом инстансе, где пользователь зарегистрирован
- Подпись в пункте 4 каждый раз новая. Один и тот же challenge второй раз не принимается

## Картинки и расширение схем данных

1. Картинки у: Unit, Instances, Instance Settings, Глобального пользователя, Групп
    - разрешение 192х192px
    - расширение png
    - размер <= 128КБ
    - картинки отдаются по uuid единой ручкой на весь бек, но с проверкой прав по токену
    - картинки хранятся в отдельной таблице pg - icons
    - в pg картинка имеет бинарный формат
    - исходное имя не хранится
    - во всех связанных сущностях передаётся ссылка на таблицу icons
1. Добавление полей под кастомизацию глобального пользователя, профиль пользователя и его настройки хранятся локально и отсылаются в инстансы по подпискам
    - ru/en
    - регион utc +X
    - настройки отображения интерфейсов
        - предпочитать code view или зарендеренный md

## Новые сущности + рефактор имён

1. Repo -> удаление
1. UnitNode -> UnitIO
1. Добавить функционал групп
    - 1 группа может содержать N Unit
    - 1 Unit может быть в N групп
    - Имя, уникальное для конкретного пользователя
    - Основная цель
        - объединение для визуала, технической задачи у него не будет
    - Важно чтобы размещение в интерфейсе элементов груп, хранилось на стороне клиента, а не бека
1. заменить глобальную уникальность имён у сущностей: unit, repo, и dashboard_panels, dashboards - на уникальность для конкретного пользователя, лучше думаю это сделать индексом в бд, а при возниконовении ошибки создания возврашщать ошибку, чтобы не плодить лишние вызовы
1. repository registry пусть генерируют картинку на основе repository_url и пусть она будет не изменяемой
