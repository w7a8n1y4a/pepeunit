# Рефактор фронтенда в клиент

Клиент — Flutter-приложение в этом репозитории. Ограничения UI лежат в коде и в `.cursor/rules/` (`client.mdc`, `hive-ui.mdc`, `hex-layout.mdc`, `hex-scale.mdc`). Здесь только то, что ещё предстоит сделать. Реализованное описано в коде и правилах.

Репозитории для проверки обновелний и скачивания ассетов:
1. По умолчанию github https://github.com/w7a8n1y4a/pepeunit
2. Запасной gitlab https://git.pepemoss.com/pepe/pepeunit/pepeunit

### Меню - /library/about

1. Назад
2. Версия клиента - без изменений
3. Проверить обновления [на вебе доступна всем, но логика отличается от нативных платформ]
4. Нативные приложения [ссылки генерируются на стороне клиента, на основе версии]
5. Соцсети - внутри без изменений
6. Поддержать проект - внутри без изменений

### Подменю /library/about/apps

Ссылка генерируется на стороне клиента. Т.е. тег берётся от текущего клиента, а не вызывается апи. Экономим на вызовах апи.

### Сота Проверить обновления в /library/about

- При нажатии воспроизводит следующую логику

1. Пользователь нажимает проверку
2. Клиент идёт по репозиториям и узнаёт тег последнего релиза. Если гитхаб чёто поломался, то вызываем гитлаб указанный выше
3. Если тег отличается в большую сторону от текущего то воспроизводится логика дальше. Если обновлений нет или у нового тега нет ассетов, то так и пишем в модалке.
4. Клиент выводит пользователю UPGRADE.md из ассетов последнего релиза. Этот файл содержит краткую сводку: добавления, изменения, фиксы.
5. [Только для нативных платформ] Снизу модалки будет кнопка обновиться
6. [Только для нативных платформ] При нажатии на кнопку обновиться скачивается бинарник исходя из текущей нативной платформы
7. [Только для нативных платформ] Если это возможно происходит автоматическое обновление

- Сейчас мы не интегрированы со сторами, так что обновление должно работать на основе бинарников из ассетов, а не внешних playmarket или аналогов apple
- После нажатия клиент запрашивает максимальную версию релиза из репозитория. Сверяет есть ли подходящий ассет

- После нажатия, таймаут 1 минуту

### Правила именования ассетов

- UPGRADE.md. Внутряк это md как в докумнетации, рендер должен соответствовать
- pepeunit-<version>-<platform>.<extension>
- pepeunit-<version>-linux.AppImage
- pepeunit-<version>-android.apk
- pepeunit-<version>-ios.ipa или app

Именно так я буду называть имена ассетов. 

### Правила генерации ссылок на ассеты

вот пример ссылки из гитлаба - https://git.pepemoss.com/api/v4/projects/212/packages/generic/release/1.5.0/pepeunit-1.5.0-android.apk
вот пример ссылки из гитхаба - https://github.com/w7a8n1y4a/pepeunit/releases/download/1.5.0/pepeunit-1.5.0-linux.AppImage

как видишь первая часть ссылки статичная, потом идёт тег и потом идёт наименования с понятным правилом. Бывает 2 сценария получения ссылки:
1. Генерация для раздела /library/about/apps. Тут генерация конечной ссылки идёт без запросов до апи гитхаб или гитлаб, просто на стороне клиента
2. Сота Проверить обновления в /library/about. Тут лучше бы предоставить нужную ссылку из готовых, которые передадут по апи (пример кстати есть в бекенде). Готовая ссылка отдаётся по совпадению блока <platform> в названии ассета. 


## Чек перед релизом

- Полный охват пользовательских ручек OpenAPI; исключения: Grafana datasource, Telegram-обвязка, Prometheus и прочий сервисный слой
- Проверка использования парамтеров из /pepeunit/api/v1/instances/current в формах и тд
- Просмотреть все интерфейсы и разгрузить их от лишних данных
- перевод документации
- перевод tooltips
- перевод ошибок - `en` в `errorTexts` (`lib/locale/error_texts.dart`) и общие строки в `lib/locale/failure.dart`
