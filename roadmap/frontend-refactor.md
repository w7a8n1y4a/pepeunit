# Рефактор фронтенда в клиент

Клиент — Flutter-приложение в этом репозитории. Ограничения UI лежат в коде и в `.cursor/rules/` (`client.mdc`, `hive-ui.mdc`, `hex-layout.mdc`, `hex-scale.mdc`). Здесь только то, что ещё предстоит сделать. Реализованное описано в коде и правилах.

## Library

- Структура устроена таким образом, чтобы поддерживать ru/en и в будущем возможность добавить другие языки
- В каждой модалке Бибилитеке будет свичер рендер исходник (render/raw) чтобы переключать между зарендереным и не зарендеренным

Рендер md:
1. Поддержка базовой структуры языка
2. Поддержка mermaid
3. Поддержка вставки картинок по ссылке
4. Поддержка :::danger ::: синтаксиса для рендера важных моментов. конечно же для warning tip и тд пусть то же работает
5. Поддержка вставки видео из yt по ссылке
6. Поддержка вставки gif по ссылке
7. Код желательно с подсветкой синтаксиса, ну хотябы там python go rust nginx и ещё какие-нибудь популярные

Raw md:
1. Рендерится как код
2. С указанием строк
3. В режиме просмтора
4. Синтаксис надо подсвечивать

- Объясняет какие фичи есть
- Позволяет заменить презентационный потенциал старого лендинга документации
- Будет работать на отдельном движке, более подходящем для презентаций

### Документация

- Это бывшая документация проекта целиком, внутри клиента. Не зависит от роли пользователя
- Дерево строится на основе md файлов, а не кода, чтобы было удобно редактировать. Оно повторяет папки `docs/<язык>/`, меню не хранит списка статей. Язык — корневая папка (`ru/`, `en/`) с одинаковыми путями; нет перевода — показываем `ru`
- Определения (`definitions.md`) и руководство пользователя (`docs/ru/user/`) в дерево не идут: их заменяет тултип. Всё остальное впитывает документация: концепция, разработчик Unit, развёртывание, устройство Pepeunit, поддержка
- Ограничений по размеру нет. Нужны большие таблицы (env), большие картинки, схемы, блоки кода с кнопкой копирования (nginx, docker, yml)

Правила:
1. Названия сущностей — как в клиенте (`menuSections` и подписи экранов). Термин API или кода — один раз в скобках. Одна сущность — одно слово во всём дереве
2. Клиент не описываем старыми словами веб-интерфейса («верхняя панель», «иконка Instances»). Если нужно сослаться на экран — цепочкой сот: `Аппараты → Создать аппарат`
3. Статья про то, чего в клиенте нет или что работает иначе, не попадает в дерево, пока её не исправят
4. Ссылка на определение сущности — на её тултип, а не на `definitions.md`
5. Ссылки между статьями — по пути внутри дерева

Что должен уметь рендер сверх списка выше:
- Широкие таблицы с горизонтальной прокруткой
- Блок кода с подсветкой, номерами строк и кнопкой копирования
- Картинки с открытием на весь экран
- Оглавление статьи по заголовкам

Схемы:
- `docs/schemas/*.svg` пока не подключаем: они устареют минимум на 2 месяца. Файлы остаются для сайта документации
- Ссылки на них в `conception/overview.md`, `deployment/schema.md`, `developer/files/struct-schema-json.md`, `development-pepeunit/mechanics/update-system.md` вернуть после актуализации

Что проверить в каждой статье перед переносом:
- Не описывает ли она старый веб-интерфейс
- Совпадают ли названия с клиентом: `Unit`, `Instance`, `Repo`, `Visualization`, `Notification` в клиенте — «Аппараты», «Сеть», «Репозитории», «Панели», «Уведомления»; «Группы» в документации нет совсем
- Не осталось ли в ней определения или инструкции пользователя, которые уже переехали в тултипы

### Тултип на всех сотах, и отдельных кнопках

Появляется у абсолютно каждой соты при:
- долгий клик ЛKМ мышкой
- клик колёсиком мыши по соте
- долгое нажатие сенсором на соте

Что показывает:
- Информационную модалку в стиле документации
- Содержит объяснение понятными пользователям словами что будет если нажать на соту
- Для инфмормационных сот, показывает какая информация отображается
- Тултип может объяснять что за раздел, например в главноем меню, соты только делают переходы. У них нажно расписть в какой раздел попадёт пользовать если нажмёт на соту, по аналогии можно и сдругими похожими по смыслу сотами
- Основная идея - предоставление краткой справочной информации. Что-то между определением и гайдом как пользоваться

Правила:
- Тултип есть абсолютно у каждой соты, пользователь должен понимать что разрабочик его не бросил, и попытался расказать что умеет каждая сота
- Не нужно раздувать размер текста. Это должна быть информация по делу
- Целевая аудитория тултипов это пользователи новички в pepeunit
- Тултипы описываются в формате .md, хранятся в корне проекта, дирректория ./tooltip/ru/... они переводятся на отдельные языки
