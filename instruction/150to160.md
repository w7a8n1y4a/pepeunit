## Порядок работы

1. Изучить текущий код и имеющиеся `AGENTS.md` во всех четырёх репозиториях. В серверном `AGENTS.md` есть ссылка на `instruction/150_to_160/backend-patterns.md`. Если карта паттернов отсутствует в рабочей копии, ориентироваться на правила самого `AGENTS.md` и существующий код.
2. Представить на ревью план с зависимостями и границами этапов. В плане описать, как backend и Python-клиент сохранят различие между `null` и пустой строкой в `.env` и как backend сообщит результат расчёта максимального размера `.env`, если схема допускает значение без конечной верхней границы.
3. Каждый этап должен давать законченный результат. Сумма добавленных и удалённых строк за этап — до 3000 по всем четырём репозиториям вместе.
4. После каждого этапа остановиться для ревью человеком. В отчёте перечислить выполненные требования, изменения контрактов, миграции, проведённые проверки и действия, оставшиеся человеку.
5. Написать интеграционные тесты. Их запуск выполняет человек. Новые модульные тесты не писать. Локальные проверки проводить согласно `AGENTS.md` с учётом этих ограничений.
6. `git add`, коммиты, push и публикации выполняет только человек. Публикация пакетов в PyPI в объём работы не входит.

## Условия перехода

- Существующие контракты сохранять, кроме тех, которые меняются по требованиям 1.6.0. Для изменённых контрактов поддержка формата 1.5.0 не требуется. Технические решения принимать самостоятельно в рамках паттернов проекта.
- При миграции допустимо удалить существующие данные `Repo`, `Unit` и `UnitIO`. Если этап использует это допущение, описать удаляемые данные в отчёте о миграции.
- При создании и удалении связи сохраняется автоматическая отправка `SchemaUpdate` со стороны backend устройству на стороне Input, если оно объявляет этот базовый Input.
- Лимитирование MQTT-трафика выполняет EMQX. MessageProcessor ведёт учёт полученных сообщений и байтов и валидирует данные по схеме.
