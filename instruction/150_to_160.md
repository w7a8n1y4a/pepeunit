# Переход Backend Pepeunit с 1.5.0 на 1.6.0

**Цель текущего этапа — реализовать готовый Backend 1.6.0 в существующем `pepeunit_server`, включая MessageProcessor, DataPipe, API, миграции и связанные тесты. После выполнения активных задач и принятия владельцем каждого результата серверный переход должен быть завершён и проверен на тестовых стендах.**

## Область работ

| Репозиторий / область | Что разрешено сейчас |
| --- | --- |
| `pepeunit_server` | Серверный код Python и Go, миграции, сборка и запуск серверного образа, связанные тесты и их конфигурация |
| `pepeunit_python_client` | Только изменения, необходимые серверным интеграционным и нагрузочным тестам; без самостоятельного расширения SDK |
| Тестовые репозитории из задачи 05 | Владелец создаёт их вручную по ходу работы; агент готовит и использует только нужные тестам файлы |
| `pepeunit` | Только этот план; Flutter, UI, клиентскую версию и сборки не менять |
| `pepeunit_go_client`, `pepeunit_micropython_client`, `pepeunit_esp_idf_client` | Не изменять, не обновлять зависимости, не собирать и не тестировать в рамках этого этапа |
| `pepeunit_deploy`, рабочие инстансы и реальные Unit | Изменения и рабочее обновление вне текущего этапа; тестовые стенды подготавливает владелец |

Go-код MessageProcessor в `pepeunit_server/data_pipe/` входит в Backend; он не является Go SDK. Серверные API поиска, эмуляции, аналогов и конструктора входят в работу, их клиентские интерфейсы — нет. Генерация README Unit остаётся серверной функцией, а написание документации проекта в этап не входит.

Исходные требования: [типизация схем](../docs/ru/roadmap/type-for-schemas.md) и [MessageProcessor](../docs/ru/roadmap/message-processor.md), только в указанной выше области. Читать контракты других компонентов можно; это не разрешает менять их. Реальные платежи и списания не входят в 1.6.0: реализуется только расчётная модель.

Номера и относительный порядок исходного плана сохранены. Следующие номера **исключены из текущего этапа**, не исполняются и не блокируют его завершение:

| Номера | Исключённая работа |
| --- | --- |
| 26–31 | Go, MicroPython и ESP-IDF SDK |
| 54–56, 58, 64 | Flutter: модели, редакторы, preview и интерфейс ресурсов |
| 68 | Прошивка плат и обновление реальных Unit |
| 74 | Документация и клиентские подсказки |
| 76–77 | Публикация общего релиза и обновление рабочих инстансов |

Смешанные задачи ниже ограничены серверной частью. Завершение этого этапа не означает переход всей клиентской экосистемы на 1.6.0; её работы требуют отдельного задания владельца.

## Правила выполнения

1. Выполнять активные задачи строго по возрастанию номеров. После изменений и проверок передавать конкретные файлы владельцу на ревью; следующий шаг — после его принятия. При продолжении учитывать фактический код и последнее ревью, не начинать инвентаризацию заново.
2. Писать готовый код прямо в штатных модулях существующих репозиториев. Переиспользовать текущие сервисы, модели, конфигурацию и тестовый запуск. Никаких отдельных прототипов, копий Backend или реализации в `instruction/`. Для Python соблюдать существующие слои `app/`, для Go — `data_pipe/`; фикстуры размещать в тестовых данных. Независимость от БД/MQTT означает чистые функции и типы внутри продукта.
3. Делать только необходимое текущей задаче. Не создавать лишние абстракции, универсальные движки, новый toolchain, сторонние рефакторинги, отчёты или документацию. `docs/en/**`, `docs/ru/**`, sidebar и конфигурацию сайта не менять. Решения и результат ревью сообщать кратко в чате.
4. **Тесты — минимальные и достаточные для изменённого поведения.** Сначала использовать существующие; новые добавлять только для непокрытого требования, значимой границы или регрессии. Не тестировать очевидную работу библиотек, не зеркалить реализацию и не плодить дублирующие или комбинаторные наборы ради количества. Перечни «Проверить» ниже задают поведение, а не требование написать отдельный новый тест на каждый пункт.
5. Запускать относящиеся к изменению проверки и обязательные проверки репозитория. После успеха не расширять и не повторять прогоны без нового изменения, сбоя или конкретного риска. Полный сквозной прогон — в задаче 67, нагрузочный — в 69, проверки окончательных артефактов — в объёме задачи 75. Для правки текста достаточно проверки diff; тесты продукта не нужны. Обязательные проверки сохранности данных, прав, учёта и миграции сокращением работы не отменяются.
6. Если задача не помещается в небольшое ревью, кратко обозначить `NN.a`, `NN.b` с границами и выполнить первую часть. Не сдавать одно разбиение вместо реализации. Весь номер закрывается после всех частей. Если проверка явно отложена самим планом, как baseline 00 → 08, владелец принимает доступную часть для продолжения; отложенная проверка остаётся обязательной.
7. Новый путь включать на тестовом стенде или временным флагом. Пока соответствующая интеграционная задача не выполнена, сохранять рабочий путь 1.5.0. Созданный модуль затем подключать к реальным серверным потребителям; тестовый дубль не заменяет интеграцию.
8. Репозитории, токены, аккаунты, внешние ресурсы и стенды создаёт владелец в задачах **РУКАМИ**. Не создавать дополнительные тестовые репозитории вне набора задачи 05. До их появления готовить нужные файлы в тестовых данных Server; после создания использовать переданные владельцем URL и версии. Не скрывать недоступные обязательные ресурсы через `skip`.
9. Соблюдать `AGENTS.md` целевого репозитория и запреты Git. По умолчанию сдавать изменения в рабочем дереве, включая новые неотслеживаемые файлы. «Готова» означает проверена и принята владельцем, а не объявлена готовой агентом.

Задачи 01–04 закрепляют правила через необходимые модели, типы и тестовые данные в целевом коде. Они не требуют отдельного пакета спецификаций и не переносят досрочно всю реализацию следующих задач. Если нужный контракт уже есть, проверить и переиспользовать его.

Если не указано иное, задача выполняется в **`pepeunit_server`**. Изменения Python SDK сдаются отдельно и только в пределах тестовой необходимости. Ручные действия ограничены тестовым окружением.

## Этап A. Исходное состояние и контракты

### 00. Исходное состояние Backend 1.5.0

- **Сделать:** проверить текущий commit, сборку и тесты Server, MQTT-подписчиков, state/log/команды, ENV/схемы, выбор target, Release Assets, DataPipe, флаги и миграции БД. Проверить, какую часть Python SDK используют тесты. Не инвентаризировать клиент и остальные SDK.
- **Проверить:** доступные локальные проверки; baseline на изолированном стенде завершить в задаче 08. Кратко сообщить точки изменения и недостающие условия, без файла отчёта.

### 01. Формальный контракт `unit.yml`, словаря и сериализации

- **Сделать:** закрепить все поля из исходника, допустимые значения, версии формата, правила `base`, `variants`, `optional`, `nullable`, `extra`, `default`, `enum`, `format`, вложенности и ограничений размеров. Определить `json`, `utf8`, `bytes`, допустимые сочетания кодеков и типов, точность чисел и запрет невалидных числовых значений.
- **Сделать:** выбрать однозначное кодирование `.env`, включая кавычки, переводы строк, Unicode, `null` и пустую строку. Зафиксировать расчёт размера в байтах с экранированием и стандартными переменными. Для неограниченного значения определить явный отказ в вычислении конечного максимума либо обязательный предел; не подменять максимум размером примера.
- **Готово, когда:** каждый пример исходника имеет ожидаемое нормализованное представление; спорные случаи имеют решение и отрицательные примеры. Задачи 10–16 развивают эти же контракты; только декларации моделей недостаточно. `unit.yml`/словарь и их описания пишутся по-английски; язык будущего UI от этого не зависит.

### 02. Контракт перехода со старых Unit

- **Сделать:** определить серверное преобразование `schema_example.json`, `env_example.json`, `schema.json`, `env.json`, `pepeunit.toml` и старых топиков. Сохранить UUID, Links, DataPipe, историю и секреты; отделить переносимые значения от требующих авторского `unit.yml`.
- **Сделать:** выбрать окно совместимости/обслуживания, обнаружение возможностей, переключение подписок и поведение offline interpreted/compiled Unit. Старое устройство не считать способным читать новый формат без обновления; неподготовленному Unit возвращать явный отказ. Другие SDK и прошивки не менять.
- **Проверить:** переход старого и нового тестового потребителя, несовместимого Unit и серверных данных. Финальный серверный режим не требует старых подписчиков и суффикса `/pepeunit`.

### 03. Контракт учёта, лимитов и сбоев

- **Сделать:** определить момент события для входа, приёма, отказа, преобразования, каждого адресата, записи DataPipe, сетевой границы. Указать плательщика каждой операции, логический размер, идентичность операции для внутренних повторов и границу ответственности брокера/устройства.
- **Сделать:** закрепить UTC-час, источник и эпоху процесса, монотонную версию снимка, смену владельца/правил, атомарность лимитов Unit и владельца между процессами. Разделить реальные повторные публикации устройства, MQTT-повторы доставки и внутренние повторы платформы.
- **Сделать:** формализовать правило «час со сбоем не оплачивается»: какие сбои квалифицируют час, какие Unit затронуты, как отменяется предварительный расчёт. Достоверные наблюдения и пропуски сохранять отдельно: неизвестная нагрузка не превращается в измеренный ноль, хотя оплачиваемое потребление такого часа может быть нулевым.
- **Готово, когда:** есть ручные эталоны для часа, его границы, сбоя, повтора, смены плательщика, двух процессов и простоя хранения без сообщений.

### 04. Контракты серверных компонентов

- **Сделать:** определить API схемы/ENV/ревизий/ошибок/расходов/команд, доставку конфигурации процессору, подтверждения и восстановление пропущенных событий. Развивать существующий Go-процесс в Server; выбрать границу процесса, health и жизненный цикл.
- **Сделать:** закрепить поддерживаемую область UCUM 2.2, округление, переполнение и отказ для неподдерживаемых единиц. Для `selected-link` — принадлежность связи, права, извлечение `data` и проверку Input.
- **Сделать:** определить серверный объём задач 57, 59–63. Для расчётной ставки — модель ёмкости, резерв 10%, периоды и предел роста N%/N времени без списаний.
- **Проверить:** необходимые примеры запросов, ответов и ошибок для серверных потребителей и Python-тестов. Не создавать интерфейсы UI и не обещать готовность ещё не реализованного API.

**Контрольная точка:** Контракты и исходное состояние приняты; дальнейшая реализация использует эти же типы и данные.

## Этап C. Ядро типов в Backend

### 10. Словарь платформы и проверка структуры YAML

- **Сделать:** `dictionary.yml` версии 1, безопасный разбор YAML, версии формата, допустимые ключи/значения `search`, `docs`, `env`, `input`, `output`; понятные ошибки с путём поля. Ограничить размер и вложенность документа, определить поведение дубликатов ключей.
- **Проверить:** все пять типов Unit, оба execution type, платформы и роли из исходника; неизвестная версия/поле/значение отклоняются согласно задаче 01.
- **Готово, когда:** структура проверяется без БД, MQTT и сети.

### 11. Нормализация схем, `base` и `variants`

- **Сделать:** раскрытие только явно указанных базовых IO; применение defaults; `variants` как объект с обязательным `action`, единственным вариантом и запретом остальных полей. Определить допустимость переопределения `base` по контракту.
- **Проверить:** полный базовый набор из исходника, его отсутствие, неверное направление IO, неизвестный base, рекурсия/недопустимое смешивание полей, необязательное поле и nullable.
- **Готово, когда:** результат детерминирован и имеет стабильную версию/отпечаток для кэшей и последующих ревизий.

### 12. Проверка payload и кодеки

- **Сделать:** проверка bool/int/float/string/object/array/any/bytes; min/max, enum, UUID, min/max_items, max_bytes, обязательных и лишних полей. `any` допускает JSON `null`; bytes сохраняет исходные байты; utf8 string не требует JSON-кавычек.
- **Проверить:** границы размеров в UTF-8, пустое значение, вложенная произвольная часть, массивы, bool против int, испорченный JSON/UTF-8, числовые границы. Ошибки не содержат секреты и полный произвольный payload.
- **Готово, когда:** есть единые машинные коды ошибок и эталоны для всех потребителей.

### 13. Преобразование величин

- **Сделать:** преобразования одинаковой физической величины по UCUM 2.2, включая масштаб и смещение; вложенные поля и массивы в согласованных пределах. Сохранить исходное значение отдельно от преобразованного.
- **Проверить:** секунды/миллисекунды, температура со смещением, одинаковая единица, несовместимые величины, неизвестная единица, float→int, округление, переполнение и выход за диапазон адресата.

- Часовой учёт проверен на повторах, сбоях, смене плательщика/эпохи и границе UTC-часа; хранение учитывается без сообщений, история имеет TTL 90 дней. Пропуски не подменяются нулём, час со сбоем не оплачивается; реальных списаний нет.
- Серверные сборки, интеграция, нагрузка, миграция с копии 1.5.0 и восстановление подтверждены на согласованных стендах. Данные, UUID, Links, секреты и старая история сохранены.

Это готовность **серверной части 1.6.0**. Клиент, прочие SDK, аппаратная приёмка и рабочее развёртывание не входят в критерии и не объявляются завершёнными.

## Проверки и сдача

Перечисленные в задачах сценарии проверять существующими тестами, дополняя их только при реальном пробеле. Общие векторы использовать повторно; для границы часа и интервалов — управляемые часы, а не ожидание реального часа. Команды выбирать по фактическому окружению и `AGENTS.md`; не запускать меняющий файлы `make lint` ради проверки и не обращаться к рабочим сервисам из тестов.

Перед ревью просмотреть diff и новые файлы. В сообщении достаточно: **номер → репозиторий и ссылки на файлы → что работает → проверки/пропуски → оставшиеся ограничения**. Отдельный отчёт, журнал или MR без запроса не создавать. Статус определяется кодом, проверками и фактическим решением владельца, а не наличием записи в плане.
