# Переход Pepeunit с 1.5.0 на 1.6.0

Это инструкция для будущей реализации. Создание этого файла не означает начало миграции, изменение версий или готовность перечисленных возможностей.

Объём перехода задан двумя документами:

- [Типизация для схем](../docs/ru/roadmap/type-for-schemas.md).
- [MessageProcessor](../docs/ru/roadmap/message-processor.md).

Другие открытые roadmap-файлы не являются дополнительными требованиями этого перехода. Однако перечисленные в типизации поиск, эмулятор, подбор аналогов, конструктор систем и генерация README включены в план. Для конструктора предусмотрен минимальный законченный сценарий на типизированных IO; отдельная MCP-система сюда не входит.

## Как выполнять план

1. Выполнять задачи по номерам, последовательно. Каждый номер — отдельное задание агенту и отдельный результат для ревью. Заголовок этапа не является заданием реализовать весь этап за один раз.
2. Задачи с пометкой **РУКАМИ** выполняет владелец проекта. Агент заранее готовит файлы, шаблоны и инструкции; создание внешних репозиториев, аккаунтов, токенов, инфраструктуры и публикации вынесены отдельно.
3. Обычная задача должна помещаться в один небольшой MR/PR одного репозитория. Если не помещается, до реализации разделить её на подзадачи `NN.a`, `NN.b` с отдельными критериями готовности. Особенно это относится к переносам обработчиков, библиотекам и UI.
4. Новый режим сначала доступен только на тестовом стенде или под временным переключателем. Промежуточные изменения не должны незаметно включать новый путь на рабочих инстансах.
5. Следующая задача начинается после ревью предыдущей. Независимые части намеренно перечислены последовательно: цель — небольшой контекст и понятная проверка каждого изменения.
6. Для каждого результата записывать: репозиторий, commit/MR, принятые решения, выполненные проверки, ожидаемые пропуски, способ отката и оставшиеся ограничения. Поле «готово» ставить только после проверки результата.
7. После каждого этапа проверять его контрольную точку. Нельзя компенсировать незавершённые задачи обещанием доделать их после 1.6.0.

Пример задания агенту:

> Выполни только задачу NN из instruction/150_to_160.md в указанном репозитории. Сначала прочитай результаты её предпосылок и местные инструкции. Реализуй указанный объём, добавь проверки поведения, подготовь краткое описание для ревью. Не начинай следующую задачу и не создавай внешние ресурсы. Если задача слишком велика или контракт противоречив, подготовь конкретное разбиение или решение до изменения зависимого кода.

## Исходная точка и репозитории

Этот репозиторий — Flutter-клиент и документация. В нём нет всей серверной реализации. План опирается на локальную [карту репозиториев](../docs/ru/development-pepeunit/maps.md), описание текущих [схем](../docs/ru/developer/files/struct-schema-json.md), [архивов](../docs/ru/developer/files/struct-archive-update.md), [DataPipe](../docs/ru/deployment/dependencies/datapipe.md) и [интеграционных тестов](../docs/ru/development-pepeunit/tests/integration-test.md). Перед серверными изменениями нужно проверить фактический код соответствующего репозитория.

| Обозначение | Репозиторий / зона ответственности |
| --- | --- |
| Client | `pepeunit`: Flutter, документация RU/EN, подсказки |
| Server | `pepeunit_server`: Backend, текущий Go DataPipe, будущий MessageProcessor, API, миграции, серверные тесты |
| Deploy | `pepeunit_deploy`: сборка, запуск, конфигурация, мониторинг, обновление и восстановление |
| Python SDK | `pepeunit_python_client` |
| Go SDK | `pepeunit_go_client` |
| MicroPython SDK | `pepeunit_micropython_client` |
| ESP-IDF SDK | `pepeunit_esp_idf_client` |
| Fixtures | Новые тестовые репозитории, подготовленные в задачах 05–07 |
| Units | Репозитории реальных Unit и их версии под новые библиотеки |

Названия новых тестовых репозиториев ниже — предлагаемые, а не уже существующие адреса. Новый отдельный репозиторий для MessageProcessor не требуется автоматически: сначала проверить возможность развития Go-процесса в Server. Решение о процессе, контейнере и месте сборки зафиксировать в задаче 04.

В текущем Client `lib/client_version.dart` задаёт `1.5.0` по умолчанию через `CLIENT_VERSION`, а `pubspec.yaml` содержит отдельную сборочную версию. Переход версии — отдельная релизная задача; менять только одно число в `pubspec.yaml` недостаточно.

## Результат, который должен дать 1.6.0

- Автор Unit описывает метаданные, ENV и типизированные IO в английском `unit.yml`; английский `dictionary.yml` определяет общие правила и явно подключаемые базовые IO.
- Backend читает `unit.yml` целевого коммита, формирует `.env` и `io_topics.yml`, вычисляет максимальный размер `.env`. На устройство поставляются программа и `.env`, а топики загружаются в рантайме.
- MessageProcessor обрабатывает новый формат топиков `domain.com/<uuid>`, валидирует сообщения, преобразует совместимые величины, пересылает сообщения и передаёт исходное сообщение этапу DataPipe.
- Backend перестаёт подписываться на MQTT и инициировать обновление схемы устройства. MQTT-настройка EMQX и выдача доступов остаются в Backend; обработка сообщений и отправка команд идут через MessageProcessor.
- Работают две базовые часовые таблицы ClickHouse: ресурсы инстанса и расходы Unit. Учёт переживает повторы и перезапуски, разделяет плательщиков, имеет историю 90 дней и не списывает средства за сбои.
- Клиент и библиотеки используют новый контракт. Все пользовательские сценарии, перечисленные в документе о типизации, доступны и проверены.
- Есть проверенный путь обновления существующего инстанса 1.5.0, миграции его Unit и связей, а также восстановление из резервной копии.

Раздел «будущая монетизация» в исходнике включён как модель и проверяемый расчёт ставки в режиме без списаний. Реальные платежи, долговечная история списаний и ежедневное списание прямо обозначены исходником как будущая работа: их не включаем в 1.6.0. Решения о формуле ставки и трактовке сбоев требуется зафиксировать заранее; молча придумывать финансовые правила в реализации нельзя.

## Этап A. Зафиксировать контракты и исходное состояние

### 00. Инвентаризация 1.5.0

- **Где:** последовательно Server, Deploy, Client, четыре SDK; результат — единый отчёт в документации.
- **Сделать:** записать реальные теги/коммиты, команды сборки и тестов, MQTT-подписчиков, обработчики состояния/логов/команд, форматы ENV/схем, правила целевой версии, Release Assets, сборку DataPipe, флаги и миграции БД. Проверить распределение MQTT по процессам.
- **Проверить:** получить воспроизводимый прогон 1.5.0 на изолированном стенде после задачи 08; до него сохранить доступные локальные результаты и список недостающих ресурсов. Не объявлять baseline подтверждённым раньше этого прогона.
- **Результат для ревью:** карта точек изменения и список существующих тестов. Разделить «подтверждено кодом» и «известно только из документации».

### 01. Формальный контракт `unit.yml`, словаря и сериализации

- **Где:** Server, спецификация и примеры без подключения к рабочему пути.
- **Сделать:** закрепить все поля из исходника, допустимые значения, версии формата, правила `base`, `variants`, `optional`, `nullable`, `extra`, `default`, `enum`, `format`, вложенности и ограничений размеров. Определить `json`, `utf8`, `bytes`, допустимые сочетания кодеков и типов, точность чисел и запрет невалидных числовых значений.
- **Сделать:** выбрать однозначное кодирование `.env`, включая кавычки, переводы строк, Unicode, `null` и пустую строку. Зафиксировать расчёт размера в байтах с экранированием и стандартными переменными. Для неограниченного значения определить явный отказ в вычислении конечного максимума либо обязательный предел; не подменять максимум размером примера.
- **Готово, когда:** каждый пример исходника имеет ожидаемое нормализованное представление; спорные случаи имеют решение и отрицательные примеры. `unit.yml`/словарь и их описания пишутся по-английски; язык UI от этого не зависит.

### 02. Контракт перехода со старых Unit

- **Где:** Server, описание совместимости и миграции.
- **Сделать:** определить переход с `schema_example.json`, `env_example.json`, `schema.json`, `env.json`, описаний `pepeunit.toml` и старых топиков. Записать, какие метаданные переносятся автоматически, какие требуют автора Unit, и как сохраняются UUID, Links, настройки DataPipe, история и секреты.
- **Сделать:** выбрать временное окно совместимости или окно обслуживания. Зафиксировать матрицу старых/новых Server, Client, SDK и Unit, механизм обнаружения возможностей, порядок переключения подписок и поведение офлайн-устройств. Не предполагать, что старое устройство самостоятельно прочитает YAML или `.env`.
- **Готово, когда:** существует маршрут для interpreted и compiled Unit, включая промежуточную прошивку при необходимости; отдельно описан отказ для немигрируемого Unit. Финальное состояние 1.6.0 не оставляет обязательных старых подписчиков и суффикса `/pepeunit`.

### 03. Контракт учёта, лимитов и сбоев

- **Где:** Server, спецификация счётчиков и примеры расчётов.
- **Сделать:** определить момент события для входа, приёма, отказа, преобразования, каждого адресата, записи DataPipe, сетевой границы. Указать плательщика каждой операции, логический размер, идентичность операции для внутренних повторов и границу ответственности брокера/устройства.
- **Сделать:** закрепить UTC-час, источник и эпоху процесса, монотонную версию снимка, смену владельца/правил, атомарность лимитов Unit и владельца между процессами. Разделить реальные повторные публикации устройства, MQTT-повторы доставки и внутренние повторы платформы.
- **Сделать:** формализовать правило «час со сбоем не оплачивается»: какие сбои квалифицируют час, какие Unit затронуты, как отменяется предварительный расчёт. Достоверные наблюдения и пропуски сохранять отдельно: неизвестная нагрузка не превращается в измеренный ноль, хотя оплачиваемое потребление такого часа может быть нулевым.
- **Готово, когда:** есть ручные эталоны для часа, его границы, сбоя, повтора, смены плательщика, двух процессов и простоя хранения без сообщений.

### 04. Контракты компонентов и пределы первой реализации

- **Где:** Server; согласуемые контракты для Client, SDK и Deploy.
- **Сделать:** определить API получения схемы/ENV/ревизий/ошибок/расходов, API команд, доставку изменений конфигурации в MessageProcessor, подтверждения и восстановление после пропущенного события. Выбрать границу процесса, health checks и управление его жизненным циклом.
- **Сделать:** определить правила преобразований UCUM 2.2, округления и переполнения; выбранную поддерживаемую область UCUM и явный отказ для неподдерживаемых обозначений. Для `selected-link` закрепить проверку принадлежности связи и прав, извлечение `data` и проверку схемы адресата.
- **Сделать:** закрепить минимальный объём поиска, подсказок DataPipe, эмулятора, аналогов, конструктора и генерации README из задач 57–64. Для будущей ставки выбрать измеряемую модель ёмкости, резерв 10%, периоды, параметры N%/N времени и режим расчёта без списаний.
- **Готово, когда:** контракты имеют примеры запросов/ответов и ошибок; нет открытых решений, от которых зависит реализация следующего этапа. Имена будущих API и настроек не выдаются за существующие.

**Контрольная точка A:** понятны формат, совместимость, семантика учёта и границы компонентов. Изменённый контракт далее требует обновить его примеры и зависимые проверки.

## Этап C. Реализовать независимое ядро типов

### 10. Словарь платформы и проверка структуры YAML

- **Где:** Server, отдельный модуль контрактов.
- **Сделать:** `dictionary.yml` версии 1, безопасный разбор YAML, версии формата, допустимые ключи/значения `search`, `docs`, `env`, `input`, `output`; понятные ошибки с путём поля. Ограничить размер и вложенность документа, определить поведение дубликатов ключей.
- **Проверить:** все пять типов Unit, оба execution type, платформы и роли из исходника; неизвестная версия/поле/значение отклоняются согласно задаче 01.

## Этап G. Часовой учёт ресурсов и устойчивость

Здесь создаются две базовые таблицы. Детали минутного мониторинга остаются в Prometheus. Учёт операций, журнал неподтверждённых батчей и метаданные миграции не требуют превращать каждую метрику в отдельную часовую строку.

### 42. Две таблицы ClickHouse и чтение последних версий

- **Где:** Server, миграции ClickHouse.
- **Сделать:** таблицы ресурсов инстанса и расходов Unit на `ReplacingMergeTree` с версией. Для Unit ключ включает инстанс, Unit, час, плательщика, версию правил, источник и эпоху; для VM определить ключ активного сборщика и поведение его смены. Изменяемые счётчики не входят в ключ замещения.
- **Сделать:** числовые счётчики колонками; TTL часовой истории 90 дней; запросы выбирают последнюю версию каждого полного ключа до суммирования. Согласовать допустимую задержку физического удаления TTL.
- **Проверить:** `100 → 230 → 310` даёт `310` до фонового merge; повтор версии не увеличивает итог; два источника суммируются; одинаковая версия не допускает разного содержимого. Разные плательщики/правила не замещают друг друга.
- **Готово, когда:** корректность чтения не зависит от фонового merge; миграция не удаляет существующие данные DataPipe.

### 43. Накопитель расходов Unit

- **Где:** Server / MessageProcessor.
- **Сделать:** общий для инстанса механизм накопления по Unit/часу из событий этапа F; сообщения в буфере учёта не хранить. При нескольких процессах явно разделить непересекающиеся вклады и доставку в общий writer.
- **Сделать:** входящие/принятые/отклонённые сообщения, байты, преобразования, каждый исходящий адресат, направления и категории внешнего обмена. Внутренние повторы дедуплицировать по контракту операции.
- **Проверить:** fan-out, частичный успех, повтор, отключённый DataPipe, смену плательщика/правил внутри часа и создание новых Unit владельцем.
- **Готово, когда:** эталонный сценарий даёт точные колонки счётчиков; сырой payload не остаётся в памяти учёта.

### 44. Общий writer и неподтверждённые батчи

- **Где:** Server.
- **Сделать:** общий батч изменившихся накопленных итогов каждые 5 секунд или при пороге количества. Один отправленный снимок неизменяем; новые события накапливаются отдельно. На ошибке не очищать неподтверждённый батч.
- **Сделать:** постоянное хранение неподтверждённых снимков и правила подтверждения; восстановление после рестарта, ограничение буфера/диска и поведение при его исчерпании. Если допускается потеря ещё не сохранённого окна, явно измерить его и пометить затронутый час неоплачиваемым по задаче 03.
- **Проверить:** insert завершился, но ответ потерян; ClickHouse недоступен; рестарт между сохранением/insert/ack; новые события во время retry; отсутствие роста памяти без границ.
- **Готово, когда:** повтор отправляет ту же версию, не удваивает расход и не затирает новые события.

### 45. Граница часа, эпохи и смена владельца

- **Где:** Server.
- **Сделать:** закрытие предыдущего часа с обязательной постановкой итогового снимка на запись, новый накопитель, новая эпоха после перезапуска; сохранение старого вклада при старте с нулём. Определить поведение опоздавшего события и коррекции времени.
- **Проверить:** 23:59:59→00:00:00 UTC, остановку прямо на границе, два процесса, смену владельца/правил, retry старого часа после открытия нового, смену лидера writer.
- **Готово, когда:** итог принадлежит плательщику события, источники не пересекаются, старый час не пропадает при рестарте.

### 46. Подтверждённые записи и логический размер DataPipe

- **Где:** Server / DataPipe.
- **Сделать:** событие оплачиваемой записи только по подтверждению; фиксированные правила логического размера, изменение объёма при добавлении/замене/удалении/истечении срока. Согласовать исход insert с неопределённым результатом и повтором.
- **Проверить:** LastValue, NRecords, TimeWindow, Aggregation и остальные существующие политики; одинаковый повтор батча; замена значения другого размера; очистка и TTL.
- **Готово, когда:** логические байты Unit не подменяются физическим размером ClickHouse; отложенное физическое удаление не ломает логический учёт срока хранения.

### 47. Байт-секунды хранения без новых сообщений

- **Где:** Server.
- **Сделать:** интегрирование текущего логического объёма по времени, тики без входящих сообщений, разбиение на границах часов, смены плательщика/правил и события удаления.
- **Проверить:** постоянные 100 байт в течение часа дают 360000 байт-секунд; изменение объёма посередине; TTL без новых записей; простой процесса, восстановление и сверку объёма.
- **Готово, когда:** хранение учитывается без активности Unit, а восстановление не начисляет повторно уже учтённый интервал.

### 48. Сборщик ресурсов VM и контейнеров

- **Где:** Server.
- **Сделать:** один активный сборщик на инстанс с передачей лидерства; сбор раз в минуту. Logporter — контейнеры; экспортер VM — ёмкость, занятость, доступность с учётом ограничений. CPU-секунды, RAM, занятый/свободный диск, операции/байты I/O и сетевые направления.
- **Проверить:** два кандидата в сборщики, потерю лидерства, сброс счётчика после рестарта, недоступный экспортер, пропущенный тик и ограничения контейнеров/VM.
- **Готово, когда:** экспортируется измеряемое состояние с временем/качеством наблюдения; контейнерные суммы не ошибочно считаются всей ёмкостью VM.

### 49. Метрики БД, пулов, очередей и сетевые настройки

- **Где:** Server.
- **Сделать:** размеры PostgreSQL/ClickHouse из самих БД, занятость пулов соединений, воркеров и очередей, задержки и ошибки. Добавить настройки лимитов скорости по направлениям, квоты трафика и её периода; ручных значений достаточно, интеграция с провайдером необязательна.
- **Проверить:** источник недоступен, недостаточно прав, период квоты сменился, значение настройки изменено, физический размер отличается от логического объёма Unit.
- **Готово, когда:** происхождение каждой метрики известно, недостающие данные отмечены как пропуск, а настройки имеют валидацию и права доступа.

### 50. Часовая агрегация VM

- **Где:** Server.
- **Сделать:** для занятости — last/min/max/интеграл; для счётчиков — прирост за час; длительность наблюдений и пропуски. Раз в минуту писать накопленный итог текущего часа, отдельно гарантировать закрытие предыдущего.

- **Готово, когда:** отчёт объясняет точность минутного сбора; краткий пик не обещан как полностью измеренный, Prometheus остаётся мониторингом.

### 51. API расходов, состояния и прогноза

- **Сделать:** чтение последних версий таблиц, расходы за период, скорости из сумм, средние из интегралов, текущий статус и простой объяснимый прогноз исчерпания ресурсов с оценкой достаточности данных.

- **Готово, когда:** исторический расход выбирается по плательщику записи, а не текущему владельцу Unit; неизвестный прогноз не заменяется выдуманным числом.

### 52. Неоплачиваемые часы и деградация учёта

- **Проверить:** частичный час со сбоем, полный простой, потерянный хвост буфера, отложенное обнаружение сбоя, восстановление без повторного начисления.
- **Готово, когда:** измеренная нагрузка не стирается, но неоплачиваемый час даёт нулевое оплачиваемое потребление; отсутствие наблюдения явно видно.

### 53. Расчёт будущей ставки без списаний

- **Сделать:** модель задачи 04: почасовой результат, пересчёт не чаще согласованного минутного периода, резерв 10%, ограничение роста N% за N времени; проверка суммарных пользовательских выделений относительно доступной мощности. Определить, как минутные расчёты формируют ставку часа.
- **Проверить:** низкую/высокую загрузку, попытку выделить 120% ёмкости, резкий скачок, смену параметров, недостоверные/пропущенные метрики и неоплачиваемый час.
- **Готово, когда:** воспроизводимый расчёт показывает ожидаемую зависимость ставки от нагрузки и ограничение роста. Балансы и списания не меняются; формула и ограничения явно документированы.

**Контрольная точка G:** обе таблицы и их API проверены при повторах, сбоях и смене процессов; лимиты работают немедленно, история и прогноз не зависят от Prometheus.

## Обязательные сквозные сценарии приёмки

Эти сценарии дополняют проверки каждой задачи. Ожидаемые числа берутся из эталонов задачи 03; часы и интервалы в автоматических тестах задаются управляемыми часами, чтобы не ждать час реального времени.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Новый interpreted и compiled Unit | Программа + `.env`; первый runtime-запрос получает топики; выбран верный target commit |
| Полный набор примеров `unit.yml` | Fan, any/null, вложенный object, массив, UTF-8, bytes, variants, nullable ENV и универсальный пульт работают по исходному документу |
| Явные base IO | Подключены только перечисленные IO; полный набор команд, state и log работает во всех SDK |
| Неверный payload | Отказ до пересылки/DataPipe, точный код и последняя ошибка UnitIO, корректные входные/отказные счётчики |
| Fan-out с разными единицами | Для каждого адресата своё преобразование и число байтов; в DataPipe исходное значение |
| `selected-link` | Доставка только разрешённому выбранному Input; чужой Link и невалидный `data` отклонены |
| Лимит владельца | Несколько Unit и процессов не обходят общий лимит; ClickHouse не участвует в решении допуска |
| DataPipe выключен | Валидация, маршрутизация, базовые команды и входной учёт продолжают работать |
| `100 → 230 → 310`, повторы insert | До merge читается 310; повтор одной версии ничего не добавляет |
| Два источника и рестарт | Последние непересекающиеся вклады суммируются; новая эпоха не затирает старую |
| Потерянный ack ClickHouse | Тот же неподтверждённый снимок повторяется; новые события сохранены отдельно |
| Граница часа/смена плательщика | Предыдущий итог сохранён; новые вклады имеют новый час/плательщика/правила |
| Хранение без сообщений | Байт-секунды растут по времени; удаление, замена и TTL своевременно меняют логический объём |
| Неполные наблюдения VM | Пропуски не являются нулём; среднее использует длительность наблюдений; неоплачиваемость считается отдельно |
| Сбой инстанса/учёта | Затронутый час не создаёт расход средств; достоверные метрики и причина сбоя доступны |
| Ограничение будущей ставки | Резерв 10%, ограниченный рост, недопущение 120% выделений; реальных списаний нет |
| Обмен A/B | Права, преобразования, направления и категории внешнего трафика; нет циклов и повторного полезного начисления |
| Обновление схемы у offline Unit | После возвращения получены согласованные ревизии; Backend не подписывается на MQTT |
| Миграция с реальной 1.5.0 | Сохранены идентификаторы, секреты, Links, политики и старая история; непереносимые данные видны в dry-run |
| Откат после частичного перехода | Согласованно восстановлены данные, образы, ACL и устройства; нет двух обработчиков или повторных команд |

## Проверки и журнал выполнения

Команды выбирать по фактическому состоянию репозитория после задачи 00. В текущей документации Server указаны `make lint`, `make test-module`, `make test-integration`, `make test-load-mqtt`, `make test-load-rest`; Client предоставляет `make test`/`flutter test` и `make analyze`. Команды SDK нужно подтвердить в их репозиториях. Новые команды для MessageProcessor добавляются вместе с реализацией, а не считаются уже существующими.

Для каждого небольшого изменения достаточно относящихся к нему проверок и обязательного CI репозитория. Полный сквозной и нагрузочный прогон выполняется в контрольных точках и на кандидате релиза; повторять его после каждой правки текста не нужно.

Шаблон записи результата задачи:

```text
Задача: NN / NN.a
Статус: не начата | выполняется | на ревью | готова | ожидает ручного этапа
Репозиторий и commit/MR:
Предпосылки и версии контрактов:
Что изменилось:
Проверки и результаты, включая skip:
Ручные действия и переданные артефакты:
Откат / ограничения:
Решение ревью:
```

На момент создания этой инструкции все задачи 00–78 имеют статус **«не начата»**. Создан только план; реализация, создание внешних ресурсов и выпуск выполняются позднее.
