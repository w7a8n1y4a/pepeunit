# Algorithm for generating a Unit's env.json

The algorithm is applied in `4` scenarios:
1. Getting env.json: `GET /units/env/{uuid}`
1. Setting env.json: `PATCH /units/env/{uuid}`
1. Downloading the archive with the Unit program (`ZIP`, `TAR`, `TGZ`): env.json is placed in the archive
1. A Unit version change, if an env.json is saved for it: Pepeunit rebuilds the saved env.json for the new version

env.json is received by the creator of the `Unit` and by the `Unit` itself with its token. Only the creator can reset the saved env.json: `DELETE /units/env/{uuid}`; after that the `Unit` again receives a cleanly generated env.json.

## Algorithm
The algorithm is built on the priority of the following `4` representations of env.json; the smaller the number, the higher the priority:

Priority | Representation | Description
-- | -- | --
1 | `Manual` | Input by a [User](/development-pepeunit/mechanics/roles#user) in the client or through `PATCH /units/env/{uuid}`
2 | `Stored in the DB` | The env.json already saved for the `Unit` in the Pepeunit database in [encrypted](/development-pepeunit/mechanics/cipher) form
3 | `Generated` | The [standard variables](/developer/files/struct-env-example-json#standard-pepeunit-variables) generated by the [Backend](/deployment/dependencies/backend)
4 | `Target` | The variables specified by the [Unit Developer](/development-pepeunit/mechanics/roles#unit-developer) in env_example.json of the target `Unit` version

The target version is taken by the [algorithm from the update system](/development-pepeunit/mechanics/update-system#algorithm-for-calculating-the-current-unit-version).

At the end, only the keys that are present in `Target` (without the standard variables) or in `Generated` are kept. All other keys are cut off, for example variables that were removed from env_example.json in the new version.

When env.json is issued to the `Unit` or shown to the `User`, `PU_COMMIT_VERSION` with the value of the target version is always appended at the end. The value entered by the `User` is ignored.

:::warning
Until env.json is written to the database, `PU_SECRET_KEY` and `PU_ENCRYPT_KEY` are generated anew on every issue. The write happens on `PATCH /units/env/{uuid}` (in the client, the button that saves env.json): after it, these keys are taken from the database and no longer change.
:::

## Validation

Before writing with `PATCH /units/env/{uuid}`, Pepeunit validates the JSON and checks it against env_example.json of the target version: env.json must contain all the variables from env_example.json. Otherwise the error `unresolved variable` is returned. The size of env.json is limited by the `pu_instance_cipher_max_length` setting ([Encryption](/development-pepeunit/mechanics/cipher)).

## Examples of how the algorithm works

### First generation of env

Algorithm steps:
1. `Target` - taken in full
1. `Generated` - generated anew in full by the Backend and overwrite the keys obtained in the previous step
1. `Stored in the DB` - absent
1. `Manual` - absent
1. Keys that are in neither `Target` nor `Generated` are cut off

Result: an env.json in which the variables generated by Pepeunit are written over the variables of the `Unit Developer`. Such an env.json is already ready to be used in the Unit.

### The Unit changes its version automatically and the set of keys changes

Algorithm steps:
1. `Target` - taken in full from env_example.json of the new version
1. `Generated` - generated anew in full by the Backend and overwrite the keys obtained in the previous step
1. `Stored in the DB` - taken from the database and overwrite all values with matching keys obtained in the previous step
1. `Manual` - absent
1. Keys that are in neither `Target` nor `Generated` are cut off

Result: an env.json in which the variables from the new version of env_example.json are added, the removed variables disappear, and the values of the rest are kept.

If there is no env.json in the database, there will be no rebuild: at the next issue the "First generation of env" case applies.

### The user changes an existing env

Algorithm steps:
1. `Target` - taken in full
1. `Generated` - generated anew in full by the Backend and overwrite the keys obtained in the previous step
1. `Stored in the DB` - taken from the database and overwrite all values with matching keys obtained in the previous step
1. `Manual` - all keys received from the `User` overwrite the keys obtained in the previous step
1. Keys that are in neither `Target` nor `Generated` are cut off
1. The result is validated, encrypted and written to the database

Result: an env.json in which the `User`'s changes are written over the old values.

After the new env.json is written, the `Unit` will not see it by itself. Send it the MQTT command [ENV_UPDATE](/developer/mqtt/default-mqtt-command#env_update-env_update-pepeunit): `Units` → `Unit` → `Control` → `Commands` → `Update environment`.
