# MessageProcessor

DataPipe на golang становится лишь 1 из этапов MessageProcessor

## Этапы MessageProcessor

0. Все подписки сводятся к `domain.com/+` благодаря типизации
1. Учёт входящих сообщений и байтов
2. Валидация согласно схемам из [Новые схемы](./type-for-schemas.md)
3. Преобразование размерностей величин [Новые схемы](./type-for-schemas.md)
4. Пересылка в другие топики UnitIO
5. DataPipe обработка

## Перенос подписки из Backend в MessageProcessor

- Backend больше никуда не подписывается по MQTT
- Backend настраивает EMQX, выдаёт доступы и публикует команды в базовые Input. При создании или удалении связи Backend по-прежнему отправляет `SchemaUpdate` устройству на стороне Input, если у него подключён базовый `schema_update`.
- Лимитирование MQTT-трафика выполняет EMQX. MessageProcessor учитывает сообщения, полученные от брокера, включая те, которые затем отклоняет при валидации.
- Можно будет на Backend провести рефакторинг MQTT-соединений

## Обработка базовых топиков

```yaml
output:
  state: {base: state}
  log: {base: log}
```

- Обработка base Output UnitIO Идёт полностью на стороне MessageProcessor
- peepunit_server никаким образом не участвует (кроме auth на топики)
- Команды в базовые Input отправляет Backend по запросу REST или автоматически при обновлении связей.

## Хранение данных о нагрузке UnitIO

Для каждого UnitIO обоих типов, мы должны знать:
1. средний request per second (любые исходы успех/отклонение и тд)
2. средний bytes per second 
3. прирост объёма хранения в datapipe

unit_io_resources_aggregation таблица в кликхаусе:
1. start_window_datetime - начало окна начало часа 15:00 например
2. end_window_datetime - конец окна 16:00 например
3. unit_io_uuid - ссылка на unit_io
4. total_requests - общее число запросов за время окна, которые пришли/ушли в unit_io
5. total_bytes - общее числа байтов за время окна, которые пришли/ушли в unit_io
6. total_datapipe_bytes_increment - сколько данных было добавлено в datapipe (число записей на вес одной записи в целевой таблице clickhouse)
7. ttl - 90 дней

- end_window_datetime - start_window_datetime будет один час всегда
- каждый unit_io будет иметь ~ 2160 записей (за 90 дней) истории
- Текущий час пополняется постепенно, т.е. в каждый момент времени, последняя запись позволяет вычислить актуальные данные (с момента начала часа до текущего момента, чтобы было точно надо будет читать через SUM(...) GROUP BY, т.е. мерж не гарантируется)
- Если нагрузка на UnitIO 0, то запись не создаётся вообще

### Алгоритм пополнения текущего часа

Используется общий буфер аналогичный DataPipe, имеющий: settings.BufferFlushInterval (default 5c) и settings.BufferMaxSize (default 1000)

Т.е. инкременты всех UnitIO добавляются в этот буфер. Буфер в какой-то момент понимает что ему надо всё загрузить в кликхаус. Буфер пакетно вставляет изменения в кликхаус

## Хранение данных о нагрузке Инстанса

- все базовые данные берутся из logporter, пусть они даже будут не самые точные, за то единнобразные для всех инстансов

Для инстанса мы должны мониторить:
1. CPU - процент использования всех ядер
2. RAM - процент использования
3. Использование ширины сети -  процент использования
    - от лимита скорости задаваемого Владельцем
4. Общий размер данных PostgreSQL - Можно узнать запросами
    - от доступного размера PostgreSQL
    - задаётся в настройках инстанса, pu_instance_pg_size_limit
    - дефолт например 1GB сделать.
5. Общий размер данных ClickHouse - Можно узнать запросами
    - от доступного размера ClickHouse
    - задаётся в настройках инстанса, pu_instance_cc_size_limit
    - дефолт например 1GB сделать

instance_resources_samples таблица в кликхаусе:
1. create_datetime - время измерения
2. cpu_percent
3. ram_percent
4. network_width_percent
5. pu_instance_network_speed_limit - лимит скорости в байтах в секунду в текущий момент времени, позволит примерно вычислять расход трафика
7. pg_disk_percent
8. cc_disk_percent
N. ttl - 90 дней

### Алгоритм пополнения

- Сбор всех данных 1 раз в минуту, через python код
- Если какой-то из параметров превышает 90% то Владельцу приходит уведомление, но не дудос каждую минуту, например не чаще чем 1 раз в 15 минут на все метрики
- За 90 дней будет храниться ~ 129600 записей

### Сетевой трафик

- важный параметр, который часто лимитирует возможности vm у хостеров
- Владелец сможет задавать лимит трафика на месяц - например 3 TB
- Инстанс сможет высчитывать примерное потребление при при помощи поля instance_resources_samples.network_width_percent и поля instance_resources_samples.pu_instance_network_speed_limit
- таким образом проверка расхода сетевого трафика будет требовать отдельного запроса


## Новые переменные instance_settings

1. pu_instance_pg_size_limit
    - в байтах, больше 0
    - дефолт 2**30 — 1 GiB
2. pu_instance_cc_size_limit
    - в байтах, больше 0
    - дефолт 2**30 — 1 GiB
3. pu_instance_network_speed_limit
    - в байтах в секунду, больше 0
    - дефолт 2**24 — 16 MiB/с
4. pu_instance_network_monthly_traffic_limit
    - в байтах, больше 0
    - дефолт 3 * 2**40 — 3 TiB
5. pu_instance_network_traffic_reset_day
    - числа 1–31
    - дефолт 1
    - если такого дня в месяце нет — последний день месяца
