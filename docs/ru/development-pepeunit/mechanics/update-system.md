## Настройки обновления Unit

Настройки обновления хранятся в самом `Unit`, а не в `Repo`. Задаются при создании: `Аппараты` → `Создать` → `Обновления`, а позже в `Настройки` `Unit`.

Настройка в клиенте | Поле | Что значит
-- | -- | --
`Автообновление` | `is_auto_update_unit` | `Unit` сам переходит на новую версию. Выключено: версия зафиксирована на выбранном коммите
`Компилируемые` | `is_compilable_unit` | `Unit` получает не исходный код, а скомпилированный файл из [assets релиза](/developer/release-assets) для своей `Платформы`
`Теги` | `is_only_tag_update` | Для автообновления берутся только коммиты с тегом
`Платформа` | `target_firmware_platform` | Для какой платформы нужен скомпилированный файл
`Ветка` | `target_branch` | Из какой ветки берётся версия
`Коммит` | `target_commit` | Нужен, только если автообновление выключено

:::warning Допустимые сочетания
- Компилируемый `Unit` с автообновлением берёт только коммиты с тегом: `Теги` включить обязательно
- Если автообновление выключено, ветка и коммит обязательны
- Компилируемый `Unit` с выключенным автообновлением может указать только коммит с тегом
:::

## Алгоритм вычисления текущей версии Unit

Целевая версия `Unit` вычисляется на локальной копии `Repo` каждый раз заново, а не хранится:

Сначала проверяется, что ветка `target_branch` есть в `Repo`. Дальше версия зависит от настроек:

Настройки | Целевая версия
-- | --
`Автообновление` выключено | Коммит `target_commit` из ветки, найденный вместе с тегом, если он есть
`Автообновление` включено, `Теги` или `Компилируемые` включены | Последний коммит с тегом в ветке
`Автообновление` включено, `Теги` и `Компилируемые` выключены | Последний коммит ветки

Если версия не нашлась (например, в ветке нет тегов), Pepeunit возвращает ошибку `Version is missing`. Для компилируемого `Unit` дополнительно проверяется, что у выбранной версии есть файл под его `Платформу`.

Эта версия и есть значение `PU_COMMIT_VERSION` в [env.json](/developer/files/struct-env-example-json#стандартные-переменные-pepeunit), которое Pepeunit вписывает при каждой выдаче env.json. Текущая версия `Unit` - это то, что сам `Unit` прислал в [состоянии](/developer/mqtt/state-mqtt-send#формат-сообщении-в-топик-state-pepeunit).

## Когда Unit обновляется

### Обновление Repo

Прежде чем `Unit` увидит новую версию, нужно, чтобы она оказалась в локальной копии `Repo`.

1. `Repo` синхронизируется с `GitLab` или `GitHub`: Pepeunit проверяет размер на платформе, заменяет локальную копию и загружает `releases`
1. Статус `Repo` меняется на `Updated`, а при ошибке на `Error` с текстом ошибки

Как запускается | Кто
-- | --
Кнопка `Синхронизировать` в карточке `Repo` | `User`, у которого есть [доступ](/development-pepeunit/mechanics/entities#repo) к `Repo`
Каждый час в `:30` для всех `Repo` | Pepeunit
Кнопка запуска для всех `Repo` | [Admin](/development-pepeunit/mechanics/roles#admin), см. [операции](/development-pepeunit/mechanics/operations)

Если предыдущая синхронизация ещё идёт (статус `Processing`) и с её начала прошло меньше `pu_instance_repo_min_interval_sync` секунд, новую запускать нельзя. Размер копии ограничен `pu_instance_repo_max_size`.

### Обновление Unit

Pepeunit отправляет `Unit` MQTT команду [UPDATE - update/pepeunit](/developer/mqtt/default-mqtt-command#update-update-pepeunit):

1. При смене настроек `Unit` (`PATCH` `Unit`): Pepeunit пересчитывает целевую версию, обновляет `UnitIO` по новой схеме и посылает `UPDATE`
1. По кнопке `Обновить прошивку`: `Аппараты` → `Unit` → `Управление` → `Команды`. Доступна только создателю
1. Автоматически, каждый час в `:00`, для всех `Unit`, у которых включено `Автообновление`
1. По кнопке [Admin](/development-pepeunit/mechanics/roles#admin) для всех `Unit` сразу

:::info
`Unit` получает команду, только если топик `update/pepeunit` объявлен в `input_base_topic` его `schema_example.json`. Иначе Pepeunit команду не отправляет.
:::

:::warning
Для улучшения производительности синхронизация `Repo` и обновление `Unit` смещены на полчаса: сначала в `:30` обновляются `Repo`, и уже в `:00` следующего часа `Unit`. Новая версия, выпущенная после `:30`, дойдёт до `Unit` примерно через полтора часа.
:::

## Что происходит с UnitIO и env.json

При смене версии Pepeunit сопоставляет схему новой версии с уже существующими `UnitIO`:

- Топики, которых больше нет, удаляются вместе с `UnitIO`
- Новые топики получают новые `UnitIO`
- `UnitIO` остальных топиков сохраняются со своими настройками и [Permission](/development-pepeunit/mechanics/permission)
- Если для `Unit` сохранён env.json, он пересобирается по [алгоритму генерации](/development-pepeunit/mechanics/alg-env) для новой версии, чтобы в нём появились новые переменные

## Как Pepeunit узнаёт, что обновление дошло

У `Unit` есть статус обновления прошивки:

Статус | Когда
-- | --
`RequestSent` | Команда `UPDATE` отправлена. Время запоминается
`Success` | В очередном состоянии `Unit` версия равна целевой
`Error` | Не удалось отправить команду по MQTT, либо с отправки прошло больше двух `PU_STATE_SEND_INTERVAL`, а версия не изменилась

Пока статус `RequestSent`, состояние `Unit` принимается без ограничения по частоте, чтобы подтверждение пришло как можно быстрее. Статус и текст ошибки видны в клиенте: `Аппараты` → `Unit` → `Сведения` → `Обновления`.
