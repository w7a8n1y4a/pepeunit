# Вход по ключу

В Pepeunit нет паролей. Аккаунт `User` - это пара ключей `ML-DSA-87` (стандарт FIPS 204). Публичный ключ хранится на инстансе, приватный только у человека. Backend никогда не получает приватный ключ и не хранит секрет, который можно украсть вместе с базой.

:::tip Зачем так сделано?
Утечка базы данных не раскрывает входов: в ней только публичные ключи. А подпись привязана к домену инстанса и действует одну попытку, поэтому её нельзя переиспользовать на другом инстансе.
:::

## Регистрация

1. Клиент создаёт пару ключей на устройстве: `Аккаунт` → `Регистрация` → `Генерация ключа`
1. Публичный ключ уходит в Backend запросом от [Bot](/development-pepeunit/mechanics/roles#bot)
1. Backend проверяет, что это корректный ключ `ML-DSA-87` длиной 2592 байта, считает его `sha256` и сохраняет оба значения
1. Создаётся `User` с ролью `User`, статусом `Active`, сгенерированной иконкой и настройками уведомлений по умолчанию
1. Приватный ключ клиент предлагает сохранить: `Аккаунт` → `Скачать ключ`

:::danger
Потерянный приватный ключ восстановить нельзя. Другого способа войти в аккаунт у Pepeunit нет.
:::

Пользователей на инстансе не больше `pu_instance_user_max_count`. Логин необязателен и нужен только для удобного поиска, его можно задать позже: `Аккаунт` → `Настройки` → `Изменить логин`.

## Вход

Вход в клиенте: `Аккаунт` → `Вход` → `Загрузка ключа`. Он состоит из двух запросов. Оба делает [Bot](/development-pepeunit/mechanics/roles#bot): человек ещё не авторизован.

1. Клиент отправляет `sha256` публичного ключа (`hash_public_key`)
1. Backend находит `User` и возвращает `challenge` - короткоживущий JWT (HS256, подпись `PU_SECRET_KEY`) с полями `uuid`, `hash_public_key`, `domain`, `jti` и `exp`. `jti` записывается в [Redis](/deployment/dependencies/redis) на 120 секунд
1. Клиент подписывает байты `challenge` приватным ключом `ML-DSA-87` с пустым контекстом и отправляет `challenge` и `signature`
1. Backend проверяет `challenge` (подпись, срок, `type`, `domain` равен `PU_DOMAIN`), проверяет подпись по публичному ключу `User` и удаляет `jti` из Redis. Повторно использовать `challenge` нельзя
1. Backend выдаёт токен `User`

Токен `User` - JWT (HS256, подпись `PU_SECRET_KEY`) с `uuid`, `type` и `exp`. Срок жизни задаёт настройка `pu_instance_user_auth_token_expiration` из [настроек инстанса](/deployment/instance-settings). Клиент передаёт токен в заголовке `x-auth-token`.

## Токены других агентов

Токен | Кто получает | Срок
-- | -- | --
`User` | Человек после входа | `pu_instance_user_auth_token_expiration`
`Unit` | Устройство, значение в `PU_AUTH_TOKEN` | Бессрочный
`Backend` | Сам [Backend](/deployment/dependencies/backend) | Бессрочный
`Grafana` | `User`, который открывает Grafana | 120 секунд, см. ниже
`GrafanaUnitIO` | Запросы панели `Dashboard` | Без срока, привязан к панели

Каждый запрос проходит одну проверку: токен декодируется, находится `User` или `Unit`, и если статус агента `Blocked`, запрос отклоняется. Поэтому блокировка действует сразу, не дожидаясь конца срока токена.

## Вход в Grafana

`User` открывает `Grafana` из клиента. Backend выпускает для него токен `Grafana`, прячет его в Redis под одноразовым тикетом и отдаёт тикет клиенту. Тикет живёт 60 секунд и удаляется при первом использовании, так что токен не оказывается в адресной строке. Сам токен `Grafana` действует 120 секунд. Функция работает только при включённом флаге `pu_ff_grafana_integration_enable`.

## Telegram

`User` может привязать Telegram, если включён флаг `pu_ff_telegram_bot_enable`:

1. Клиент просит у Backend ссылку на бот. Backend создаёт 8-символьный код с жизнью 60 секунд и добавляет его в ссылку
1. Бот получает код и записывает `telegram_chat_id` в `User`. Один Telegram привязывается только к одному `User`
1. Дальше бот узнаёт `User` по `chat_id`, а не по токену, и заблокированного `User` не пускает
